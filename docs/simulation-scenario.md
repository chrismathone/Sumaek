# dev 수동 시뮬레이션 시나리오

작성 2026-08-01 · 대상 커밋 `f2d68c8` (인수 4 배선 완결)

이 문서는 **자동 테스트가 덮지 못하는 것**을 사람이 직접 확인하기 위한
것이다. 628건의 단위·통합과 39건의 E2E가 이미 도는 영역은 여기서 다시
누르지 않는다. 여기서 겨누는 것은 다섯 가지다.

1. **워커를 실제로 띄운 상태의 왕복** — outbox→디스패처→작업→핸들러.
   자동 테스트가 유일하게 못 도는 사슬이다(`dispatchOutbox`가 전역이라
   공유 DB에서 부를 수 없다).
2. **브라우저가 실제로 그리는 것** — 수식이 한 번만 보이는가, 표가 바깥
   스크롤을 만들지 않는가, 알림이 행을 밀지 않는가.
3. **kill switch가 사람과 자동화를 갈라 막는가** — 자동 재계산은 멈추고
   교사의 버튼은 살아 있어야 한다.
4. **KST 경계** — 오늘·기간·월이 조직 시간대로 끊기는가.
5. **역할 시야** — 학생 계정이 교사 화면에 닿지 못하는가.

각 단계는 **조작 → 기대 → 결손 신호** 순서다. 「결손 신호」가 보이면
그 자리에서 멈추고 기록한다. 기대와 다른 것을 봤다는 사실 자체가 결과다.

### 0.4 ⚠ 워커를 띄우기 전에 반드시 읽을 것

`dispatchOutbox`는 **조직 스코프가 아니라 전역**이다. 지금 `pending` 상태의
outbox 이벤트가 **569건** 쌓여 있고, 워커를 띄우는 순간 이것들이 한 번에
디스패치되어 작업이 된다. 대부분은 `notification.dispatch`·
`schedule.recalculate`라서 **알림이 무더기로 생기고 데모 반의 일정이 다시
계산될 수 있다.** 이 이벤트들은 한 번도 소비된 적이 없으므로 Inbox 멱등이
걸러 주지 않는다.

선택지는 둘이다.

- **(권장) 그냥 두고 기다린다.** 워커를 띄우고 로그가 조용해질 때까지
  둔다(`[outbox] N건 디스패치`가 더 안 나올 때까지, 대략 6~7회 순환).
  그 뒤에 3장을 시작하면 새 이벤트 1건만 깨끗하게 관찰된다.
  데모 워크스페이스의 알림·일정이 한 번 흔들리는 비용을 치른다.
- **(빠름·되돌릴 수 없음) 밀린 것을 버린다.** 아래를 Supabase SQL 편집기에서
  실행하면 569건이 소비되지 않은 채 종료 처리된다. **영구적이다.**
  데모 워크스페이스라 실무 손실은 없지만, "밀린 이벤트를 버렸다"는 사실은
  기록해 두는 편이 좋다.

  ```sql
  update outbox_events set status = 'delivered', delivered_at = now()
  where status = 'pending';
  ```

어느 쪽이든 **선택했다는 사실을 적어 두고** 3장으로 간다.

### 0.5 이 시뮬레이션은 실제 DB를 바꾼다

로컬 목이 아니라 Supabase 실 인스턴스다. 오버라이드·학습자 일정·감사 기록이
실제로 생긴다. 감사(`audit_events`)와 증거 계열 테이블은 **불변 트리거가
걸려 있어 지울 수 없다.** 되돌릴 수 있는 것과 없는 것은 12장에 정리했다.

## 3. 인수 4 본선 ② — 워커 왕복 (자동 테스트가 못 덮는 곳)

0.4를 읽고 선택을 마쳤으면 여기서 워커를 띄운다.

```bash
pnpm dev:worker
```

**3-1** 기동 로그를 확인한다.

- **기대** — `[su-maek worker] worker-… 시작 — 토픽 9개, 동시성 4`.
  **토픽 9개**여야 한다.
- **결손 신호** — 토픽이 8개다 → `schedule.materialize-learner` 등록이 빠졌다.
  이 상태면 오버라이드 이벤트가 **영구 유실**된다(작업 0건을 만들고도 outbox를
  `delivered`로 표시한다).

**3-2** 밀린 569건이 흘러가기를 기다린다. `[outbox] N건 디스패치` 로그가
더 나오지 않으면 준비 완료다. (0.4의 빠른 선택지를 골랐으면 즉시 조용하다.)

**3-3** 브라우저로 돌아가 박서윤 상세에서 **오버라이드를 「취소」** 한다.
**「개별 일정 계산」은 누르지 않는다.** 사람이 아니라 워커가 하는지를 본다.

- **기대 (워커 로그)** — 몇 초 안에
  ```
  [outbox] 1건 디스패치
  ```
  가 찍히고 `schedule.materialize-learner` 작업이 실행된다.
- **결손 신호** — 아무 로그도 없다 → 취소가 이벤트를 발행하지 않는다.
  `[job:…] … 실패` → 핸들러 오류. 로그 전문을 남긴다.

**3-4** 브라우저를 **새로 고침**한다. (워커가 쓴 것이라 화면이 자동으로
갱신되지는 않는다 — 이것도 정상이다.)

- **기대** — 「개별 일정」 표가 다시 **3행 · 전부 「같음」 · 재합류 없음**.
  오버라이드가 빠졌으니 학생이 반 공통 경로로 되돌아온 것이다.
- **결손 신호** — 여전히 2행이고 「다름」이 남아 있다 → 워커가 소비하지
  않았거나 실체화가 반영되지 않았다.

**3-5** 감사 기록을 확인한다. `/app/audit`에서 작업 필터를 쓰거나 사유로
검색한다.

- **기대** — `schedule.materialize-learner` 기록 중 **사람이 누른 것**은
  실행자가 남고, **워커가 한 것**은 자동화로 남는다. 둘이 구분된다.
- **결손 신호** — 워커가 한 것이 사람 이름으로 기록된다.

## 4. kill switch — 자동화는 멈추고 사람은 산다

이 구분이 이 제품의 약속이다. 스위치는 **자동화를 끄는 것**이지 교사를
막는 것이 아니다.

**4-1** 자동 재계산을 멈춘다.

```bash
pnpm kill-switch stop auto_reschedule --reason "수동 시뮬레이션" --actor st2000423@gmail.com
```

**4-2** 워커 로그를 본다.

- **기대** — **동작한다.** 스위치가 내려가 있어도 사람이 명시적으로 누른

  교사가 손으로 일정을 고칠 수단을 잃는다는 뜻이라 **결손이다**.

**4-5** 복구한다. 워커 로그에서 밀린 작업이 재개되는지 본다.

## 9. 점수는 내림

select id, total_score, max_score, round(total_score / nullif(max_score,0) * 100, 2) as pct from attempts where organization_id = '00000000-0000-7000-8000-000000000001' and total_score is not null order by created_at desc limit 10;

`pct`에 소수 부분이 있는 행을 골라 화면 값과 대조한다. `39.9 → 39`면 맞다.

## 10. 캘린더 셀 넘침

> ⚠ **지금 데이터로는 「+N개 더」가 나오지 않는다.** 셀당 2개까지 그대로
> 보여 주는데(`MAX_VISIBLE_ENTRIES = 2`) 데모 반은 하루에 1건뿐이다.
> 10-2를 하려면 10-2a로 넘침을 먼저 만들어야 한다. 만들지 않을 거라면
> **10-2를 「미확인」으로 적는다** — 안 보였다고 「통과」가 아니다.

**10-1** `/app/calendar?month=2026-08`에서 창을 좁혀 가며 본다.

- **기대** — 셀 높이가 **고정**(`h-28`)이고 주 행 높이가 균일하다.
- **결손 신호** — 일정 많은 날의 셀만 키가 커진다.

**10-2a** 넘침을 만든다. **휴일 등록 화면은 아직 없다**(`/app/settings`에
「휴일 달력 … 준비 중」으로 적혀 있다). 그러므로 SQL로 8월 5일에 3건을 넣는다.

```sql
insert into holidays (id, organization_id, kind, name, starts_on, ends_on) select gen_random_uuid(), '00000000-0000-7000-8000-000000000001', 'national', '시뮬레이션 넘침 ' || n, date '2026-08-05', date '2026-08-05' from generate_series(1,3) as n;
```

**10-2** 8월 5일 칸의 **「+N개 더」**를 클릭한다.

- **기대** — 그 자리에 떠 있는 창으로 나머지가 보이고, 달력 격자는
  그대로다(셀이 늘어나지 않는다).
- **결손 신호** — 클릭해도 아무 일이 없다 / 페이지가 이동한다 / 창이 화면
  밖으로 잘린다 / 셀이 커지면서 주 행이 밀린다.

**10-2b** 확인이 끝나면 **반드시 지운다.** 남기면 8/5 수업이 휴일로 잡혀
이후 일정 계산이 전부 틀어진다(엔진은 `kind`를 보지 않고 휴일 날짜를 슬롯에서
제거한다).

```sql
delete from holidays where name like '시뮬레이션 넘침%';
```

## 이 시나리오가 덮지 못하는 것

정직하게 적는다. 여기를 다 통과해도 아래는 확인되지 않은 채 남는다.

- **동시 사용자.** 두 교사가 같은 학생을 동시에 계산하면 어떻게 되는지
  보지 않는다(실체화에 자문 잠금이 있지만 사람 손으로 재현하기 어렵다).
- **워커 다중 인스턴스.** 한 프로세스만 띄운다. 리스 만료 회수는 자동
  테스트(`schedule-resume.test.ts`)에만 있다.
- **부하.** 10회 동시 제출, 대량 학습자에서의 표 성능은 대상이 아니다.
- **실패 주입.** DB 연결이 중간에 끊기는 경우, AI 공급자 장애는 다루지 않는다.
- **모바일 실기기.** 창 폭만 줄여 볼 뿐 터치·소프트 키보드는 확인하지 않는다.
- **접근성.** axe 자동 검사는 목록 화면 위주라, 이번에 새로 생긴 학생 상세의
  「개별 일정」 표는 아직 검사 대상이 아니다. 키보드만으로 정렬·페이지네이션에
  닿는지 정도는 손으로 눌러 보는 편이 좋다.
