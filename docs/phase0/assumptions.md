## 3. 용량 추정 — 계산식과 결과

모든 계산은 골프롬프트 2J의 6개 식을 그대로 사용한다. 각 식의 입력은 위 A-계열 ID를 참조한다.

### 3.1 피크 답안 RPS

```
피크 답안 RPS = 활성 학생 × 일일 테스트 수 × 테스트당 문항 수 ÷ 집중 응시 시간 × burst factor
```

| 단계 | 계산 | 결과 |
|---|---|---|
| 1일 답안 (A-13) | 200,000 × 2.4 × 10.4 | 4,992,000 ≈ **5,000,000건/일** |
| 집중 창 내 답안 (A-09: 75%) | 5,000,000 × 0.75 | 3,750,000건 |
| 집중 응시 시간 (A-09) | 16:00–21:00 = 5시간 | 18,000초 |
| **집중 창 평균 확정 제출 RPS** | 3,750,000 ÷ 18,000 | **208 RPS** |
| burst factor (수업 종료 정각 동시 제출, 5분 창) | ×3.0 | **625 RPS** |
| 임시 저장 계수 (A-15) | ×1.4 | **875 RPS** |
| **설계 수용 목표** | 올림 | **1,000 RPS** |
| **부하시험 목표 (설계의 2배, 29장)** | ×2 | **2,000 RPS** |

파생 값:

| 항목 | 계산 | 결과 |
|---|---|---|
| 24시간 평균 답안 RPS | 5,000,000 ÷ 86,400 | 57.9 RPS |
| 일평균 대비 피크 배수 | 875 ÷ 57.9 | 15.1배 (골프롬프트 "10배 burst" 기준 상회 → 이 값으로 설계) |
| 시험 시작 RPS (A-16) | 20,000 ÷ 600 | 33.3 시작/초 |
| 시험 시작 시 스냅샷 전송 | 33.3 × 250KB | 8.3 MB/s |
| 답안 쓰기 DB 커넥션 소요 | 875 RPS × 15ms | 13.1 동시 커넥션 |
| 웹 인스턴스 풀 설계 | 인스턴스 12개 × pool max 10 | 120 커넥션 (Supabase transaction pooler 여유 확보) |

### 3.2 응답 저장량

```
응답 저장량 = 하루 답안 수 × 평균 응답 크기 × 보존 일수
```

평균 응답 물리 크기 산출:

| 구성 | 크기 |
|---|---|
| 키·FK (id, organization_id, attempt_id, assessment_question_id) | 64 B |
| `payload` jsonb (객관식 60B / 단답형 180B / 서술형 1,400B, 유형 비율 55:33:12 가중) | 313 B |
| 채점 결과·신뢰도·정규화 결과 | 200 B |
| 타임스탬프·client_seq·감사 메타 | 100 B |
| **논리 소계** | **677 B** |
| 튜플 헤더 + 정렬 패딩 + 인덱스 3종 | ×2.4 |
| **평균 응답 물리 크기** | **1.63 KB** |

> 서술형 답안 본문이 8KB를 초과하면 Storage로 오프로드하고 DB에는 포인터+체크섬만 남긴다. 이 규칙이 평균 크기 상한을 보증한다.

| 시나리오 | 계산 | 결과 |
|---|---|---|
| 1일 증가분 | 5,000,000 × 1.63KB | **8.15 GB/일** |
| 핫 파티션 (180일) | 8.15 × 180 | **1.47 TB** |
| 활성 보존 (A-39: 1,095일) | 8.15 × 1,095 | **8.92 TB** |
| 1년차 실사용 (워크스페이스 50 / 학생 5,000) | 125,000/일 × 1.63KB × 365 | **74 GB** |

**결정**: `responses`는 `saved_at` 기준 **월 단위 RANGE 파티션**. 180일 초과 파티션은 `pg_dump` → Storage 아카이브 후 DETACH. `attempts`, `mastery_evidences`, `progress_events`, `audit_events`, `outbox_events`도 동일 규칙.

### 3.3 문항 자산 저장량

```
문항 자산 저장량 = 문항 수 × 평균 메타데이터 + 원본 페이지·도형·해설 자산
```

DB 측 (PostgreSQL):

| 구성 | 단위 크기 | 총량 |
|---|---|---|
| `question_versions` 메타 | 1.0 KB | 10.0 GB |
| `structured_content_blocks` (문항당 평균 9블록, jsonb) | 4.0 KB | 40.0 GB |
| `math_expressions` (A-22: 3.5개 × 700B) | 2.45 KB | 24.5 GB |
| `question_alignments` + 품질 통계 | 1.05 KB | 10.5 GB |
| 논리 소계 | 8.5 KB | 85.0 GB |
| 인덱스·GIN·튜플 오버헤드 ×2.2 | 18.7 KB | **187 GB** |

객체 스토리지 측:

| 구성 | 계산 | 총량 |
|---|---|---|
| 원본 PDF (연 12.5M 페이지 × 120KB) | 50,000/일 × 250 영업일 × 120KB | **1.50 TB/년** |
| 페이지 렌더 이미지 (300 DPI JPEG 450KB) | 12,500,000 × 450KB | **5.63 TB/년** |
| 도형 SVG (A-26: 35% × 8KB) | 10,000,000 × 0.35 × 8KB | **28 GB** |
| 해설 이미지 (10% × 60KB) | 10,000,000 × 0.10 × 60KB | **60 GB** |
| 렌더 캐시 HTML+MathML (문항당 12KB, 30일 회전) | 10,000,000 × 12KB | **120 GB** |
| **객체 스토리지 1년차 합** | | **약 7.34 TB** |

**결정**: 페이지 렌더 이미지는 반입 완료 + 검수 종료 후 90일 경과 시 **1,200px 롱에지 WebP(평균 95KB)로 다운샘플**하고 원본 300 DPI는 삭제한다. 이 규칙 적용 시 2년차부터 연 증가분은 5.63 TB → 1.19 TB로 줄어든다. 원본 PDF는 A-45 정책까지 원본 보존한다.

### 3.4 AI 처리량

```
AI 처리량 = 하루 페이지 수 × 페이지당 호출 수 × 재시도·폴백 계수
```

| 단계 | 호출 단위 | 페이지당 호출 |
|---|---|---|
| OCR (페이지) | 1 × 페이지 | 1.0 |
| 문항 영역 분리 (페이지) | 1 × 페이지 | 1.0 |
| 수식·구조 추출 (문항) | 1 × 3.2문항 | 3.2 |
| 정답·해설 검증 (문항) | 1 × 3.2문항 | 3.2 |
| 교육과정·난이도 분류 (문항) | 1 × 3.2문항 | 3.2 |
| **소계** | | **11.6 호출/페이지** |
| 재시도·폴백 계수 (429/5xx 재시도 0.18 + 2차 모델 폴백 0.07) | ×1.25 | **14.5 호출/페이지** |

| 항목 | 계산 | 결과 |
|---|---|---|
| **1일 AI 호출** | 50,000 × 14.5 | **725,000 호출/일** |
| 24시간 평균 | 725,000 ÷ 86,400 | 8.4 호출/초 |
| 반입 창 집중 (주간 6시간) | 725,000 ÷ 21,600 | 33.6 호출/초 |
| 피크 (burst ×2) | | **67 호출/초** |
| 1일 입력 토큰 | 페이지당 40,000 × 50,000 | 2.00 × 10⁹ |
| 1일 출력 토큰 | 페이지당 11,640 × 50,000 | 5.82 × 10⁸ |
| **1일 AI 비용 상한** (기준가 입력 $3/M · 출력 $15/M) | 6,000 + 8,730 | **USD 14,730/일** |
| 1년차 실사용 (하루 2,000페이지) | ×0.04 | **USD 589/일** |

**결정**: 이 상한이 A-37(조직 1일 USD 20 / 전체 1일 USD 4,000) 한도의 존재 이유다. 전체 한도 USD 4,000/일은 **1일 13,580페이지**에 해당하므로, 50,000페이지/일 용량은 상향된 유료 콘텐츠 플랜 조직에만 개별 한도로 개방한다. 80% 도달 시 경고, 100% 도달 시 신규 작업 `queued` 유지 + 승인 대기(`ai_provider:<name>` kill switch와 별개의 예산 게이트).

### 3.5 수식 렌더 처리량

```
수식 렌더 처리량 = 신규·변경 수식 수 × 대상 렌더러 수 × 골든·시각 검증 계수
```

| 단계 | 계산 | 결과 |
|---|---|---|
| 1일 신규·변경 수식 | 50,000 × 3.2 × 3.5 | 560,000개 |
| × 대상 렌더러 (A-25) | ×3 | 1,680,000 |

| 반입 창 집중 (6시간) | ÷21,600 | 93 검증/초 |
| 피크 (×2) | | **187 검증/초** |

CPU 소요:

| 렌더러 | 1건 CPU | 피크 지분 | 소요 CPU |
|---|---|---|---|

**결정**: 렌더 워커는 **4 vCPU × 2 인스턴스**로 시작한다(피크 2배 여유). Chromium은 워커 프로세스당 브라우저 1개를 재사용하고 페이지 컨텍스트만 회전한다(콜드 스타트 1.8초 회피).

## 7. 이 문서의 갱신 규칙

1. A-계열 값을 바꾸면 3장 계산을 다시 계산하고 결과 표를 갱신한다. 계산식은 바꾸지 않는다.
2. `상태 = 초기값`인 항목은 실측 데이터가 생기면 **확정**으로 승격하고 근거(측정일·측정 방법·표본 수)를 근거 열에 적는다.
3. 실측이 예측을 뒤집으면 관련 ADR을 `Superseded`로 바꾸고 새 ADR을 발행한다 (골프롬프트 2A 설계 순서 10).
4. Q-계열이 해소되면 행을 삭제하지 않고 `해소` 표시와 결정 링크를 남긴다.
